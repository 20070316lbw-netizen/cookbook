# 失败时返回空 DataFrame:数据管道里最阴险的静默 bug

## 坑长什么样

函数签名承诺返回 DataFrame,失败分支只 log 不 return,pyright 标红
(`reportReturnType`:有路径返回 None)。为了消红,顺手写了:

```python
except ConnectionError as e:
    logger.error(f"抓取失败 - {e}")
    return pd.DataFrame()   # ← 类型检查过了,坑埋下了
```

更危险的变体:把它写进**基类契约**——"失败时记录日志并返回空 DataFrame,
不向上抛异常"——意味着所有数据源都继承这个静默失败模式。

## 为什么是坑

调用方**无法区分"查到了空数据"和"出错了"**。空 DataFrame 会安静地流过
整条管道:concat 不报错、groupby 不报错、入库不报错——最后只是结果数据
莫名少了一块,排查起来比当场崩溃痛苦十倍。

数据管道的铁律:**静默的空值比异常恶劣得多。**

类型检查的红只是信使。它说的是"承诺和行为不一致",正确反应是修复不一致,
不是造一个类型正确、语义错误的值把信使打发走。

## 怎么解

让签名说实话,按语义二选一:

1. **"没数据"属于正常情况** → 返回类型改 `pd.DataFrame | None`,失败 `return None`。
   pyright 会反过来逼每个调用方先判 None 再用——错误处理被强制传染,这是好事。
2. **"没数据"不该发生、下游没法继续** → 失败分支 log 后 `raise`,
   返回类型保持 `pd.DataFrame`。语义:"要么给你数据,要么炸。"
   抓取类(EDGAR/yahoo)基本都该选这个。

## 教训

消红的手段必须同时消灭语义问题。一个函数失败时"假装一切正常"
比"当场崩溃"贵十倍——崩溃的成本在今天,静默的成本在三周后的深夜。
